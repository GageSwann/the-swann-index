## 1. Neon network transfer (the budget that took the site down)

**The limit (#140):** Neon's free plan allows **5 GB of network transfer a month for the whole project**, every branch counted (`dev` too) and every reader (local scripts, GitHub Actions, Render). Over the limit Neon **suspends the compute until the next billing period**: connections are refused ("exceeded the quota"), the API's `/health` still answers 200 but every data endpoint answers 500.

**History:** the period that started Oct 31 hit 5.40 GB on 2026-11-09 (production 4.19, dev 1.21) and Neon suspended the project that evening; the project total froze at **5.6 GB**. On Nov 20 the owner added Neon's $5 limit increase (25 GB) for one period to come back early (#151); the new period (Nov 20 – Dec 1) started at 0 GB and serves to prove the free 5 GB fits.

**Where it went (#145, measured with the transfer meter):** the site re-checked every visited page's data **hourly** (~1,000 ISR writes and ~30 MB of gzipped API responses a day, ~0.3 GB a day from Neon). Since #145 pages re-check daily and the nightly refresh is what updates them.

**What reads what now** (local copy, transfer meter):

| Reader | Before | Now |
|---|---|---|
| Nightly `tsi run` | 12.6 MB | 3.0 MB (#146 Elo carry, #147 one read per season) |
| Nightly page refresh (~60 pages) | 7.3 MB | 3.3 MB (#148 Résumé context cache) |
| A full site build (~120 pages) | 17.6 MB | 9.95 MB (2026-11-20) |
| `/rankings` · `/playoff` · week board | ~267 · ~189 · 145–200 KB | ~200 (#154) · ~152 · ~55 KB (FBS/FCS), ~100 KB (All) (#155) |
| Home page rankings | ~0.8 MB (four full rankings) | ~22 KB (`/rankings/top`, #155) |
| `/teams/{slug}` | ~87 KB | ~8 KB after #148; 42 KB with the rebuilt season's ~90 runs; **~20 KB** after #154 (history grows ~90 B per run) |
| Home page | 764 KB | same (largest left) |

**Heavy (never against Neon without the owner's OK):** `tsi backtest run` / `book`, scratch experiments, `tsi model fit`, `tsi model carry`, the backtest and migrate-with-reload workflows, `tsi ingest season`, a full replay (13.8), `pg_dump`. Run them on a **local copy** (§2) and write only results to Neon. **Light:** the nightly job, the API, site builds (but batch pushes: each web push rebuilds the site from the live API).

**Measuring:**
- The **transfer meter** (`.claude/skills/tsi-weekly-run/scripts/transfer_meter/`) is a byte-counting relay in front of a local Postgres: exact server-to-client bytes, what Neon bills. Check every new reader with it before shipping, never against Neon. Neon itself gives no per-query bytes; `pg_stat_statements` shows rows per call but is cleared whenever the compute scales to zero.
- A full `npm run build` against the local API through the relay takes ~15 minutes on this PC (the local API answers one page at a time): run it in the background.
- Measuring the site in `next dev` overcounts: dev runs `generateStaticParams` on every visit, so each team page re-read the FBS rankings (9.5 MB of a 15.8 MB pass in #148). Disable it for the measurement.
- **Nightly reading (#179):** the nightly workflow's last job (`transfer`) runs `tsi neon transfer`: one GET of Neon's project details (`data_transfer_bytes`, the period's running total, every branch), no database reads. The reading goes on the run's summary page; over 80 MB a day on average it adds a warning; on pace to pass 5 GB (from day 3 of a period, so one heavy day can't trip it) or 80% used it opens a GitHub issue "Neon transfer: on pace to go over (period from …)", then comments on that issue on later nights. The job never turns the run red (the 14:23 backup's gate counts successful runs; a red run would run `tsi run` again). Pace = average a day so far × the period's length; when Neon's period dates don't bracket now, the calendar month (UTC) is used and the summary says so. Neon says these usage fields are "not intended for billing": the console stays the reference.
- **Neon console:** the project's **Overview** shows the period's total (the number the limit uses; the Billing page shows transfer only after an overage). Each branch's Overview shows its own share, but **while the project is suspended the branch panels read 0** ("metrics are not updated for inactive projects"; seen 2026-11-20 while the project total read 5.6 GB). Per branch by API: `data_transfer_bytes` from the branch details endpoint (needs a Neon API key). The project page says "Since Nov 1" and the branch page "Since Oct 31" for the same period (time zones).
- The database is ~63 MB, so one `pg_dump` costs about that; the danger is *repeated* full reads (2.89 GB by Nov 6 ≈ 46 of them).
- **A day of site design costs ~7–10 MB per web push** (each push that changes `web/` rebuilds the site from the live API on Vercel). Until #191 CI's web job also ran a production build on **every** push, docs- and backend-only too: Nov 23 cost ~480 MB (~29 Vercel builds + 38 CI builds). CI no longer builds the site; Vercel's build is the only one. On 2026-11-23 about 16 web pushes (#156–#176) cost ~160 MB, more than the whole untouched day. Batch web changes into one push, check them first with screenshots of the local site (§9 Browser testing), and push docs-only or backend-only commits freely (they don't rebuild the site). The period's first reading (Nov 23, 0.48 GB for Nov 20–22) is in the roadmap's "Now" table.

**While suspended:** the site serves its cached pages as long as nothing expires them, so the nightly job is paused (`gh workflow disable daily-refresh.yml`): its refresh step runs even after a failed `tsi run` and would expire the pages. Vercel's build fails (it prerenders from the live API; the old site stays). Until #191 CI's web job also built the site, so pushes went red and Render deployed nothing; CI no longer reads the API. Coming back (done 2026-11-20): confirm Neon answers, Render Manual Deploy (CI was red), re-enable and run the nightly job, then redeploy the site.

## 2. Local Postgres copy

Both PCs have one; it is where heavy work runs (§1).
- **Work PC** (it can't reach Neon at all): local Postgres 17, 2014–2026 re-ingested from the CFBD disk cache, current through Nov 9; no production snapshot or pick history. #145 was measured on it.
- **Home PC:** portable PostgreSQL 17.11 (EDB binaries, no admin rights or service) in `%LOCALAPPDATA%\Programs\PostgreSQL17`, database `tsi`, trust auth on localhost only. Start it after a reboot: `pg_ctl -D "%LOCALAPPDATA%\Programs\PostgreSQL17\data" -l "%LOCALAPPDATA%\Programs\PostgreSQL17\server.log" start` (from its `bin`).
- **Point tools at it** by setting both `DATABASE_URL` and `DATABASE_URL_DIRECT` to `postgresql+psycopg://postgres@localhost:5432/tsi` for the command. Alembic and the DB tests use the direct one; setting only one sends them to `dev`.
- The server must use `timezone = UTC` (Neon's), or three API tests fail on `-05:00` timestamps.
- **After a rebuild on the local copy** (#152) the newest local run can be a rebuilt weekday without a sim (the copy has no real run after its last `tsi run`), so the local `/playoff` answers 404. Run `tsi run --no-ingest` locally to get a current run, as production has.
- Building one: re-ingest from the CFBD disk cache (`tsi ingest season --season 2014 --through 2026`, no transfer, ~11 CFBD calls for the current season, no live-only tables), or one `pg_dump` of `dev` (~63 MB of transfer, every table including snapshots and picks). Then `alembic upgrade head` and one `tsi run`.

## 3. Database and SQLAlchemy

- **SQLAlchemy 2.1:** don't `dict(session.execute(...))`; unpack rows in a comprehension. Use `.ext(postgresql.distinct_on(...))`, not `.distinct(cols)`.
- **Upserts** always go through `db/upsert.py` (batched executemany, skips unchanged rows). Never send the same primary key twice in one batch; de-duplicate first.
- **Filter by id lists** with `one_of(col, ids)` (`db/queries/filters.py`, `= ANY(array)`), never `.in_()`.
- **Alembic** autogenerate misses primary-key changes; hand-write those. Pass the short constraint name (e.g. `"basis"`), never the full `ck_table_name`.
- **numpy threads:** `tsi/__init__.py` caps BLAS at 1 thread (multithreading made our small solves ~40× slower). Scratch scripts must `import tsi` before numpy.

## 4. API performance

- **Where time goes:** locally each Neon round trip is ~30 ms, so round trips dominate. In production (Render Ohio next to Neon us-east-2) a round trip is a few ms but Render's free tier has **0.1 CPU**, so Python CPU per request dominates (≈10× local; gzip runs at level 1 for that reason, #136).
- **Measure both:** round trips with a SQLAlchemy `before_cursor_execute` counter; CPU with `time.process_time()` averaged over ~20 requests (the Windows clock ticks every 15.6 ms). Profile in-process with `TestClient(create_app())` used as a context manager (the lifespan creates the sessions).
- **Endpoints are `async` and do all database work through `deps.read(sessions, lambda s: ...)`** (#102). Never a sync endpoint with a session dependency: it deadlocked the pool under build bursts. At most 10 requests run at once (`CONCURRENT_REQUESTS`, below the 15-connection pool).
- The API engine autocommits (`make_engine(read_only=True)`, #93); every engine pings connections before use (#99); the site's API client retries transient 5xx/network failures (`web/lib/api/retry.ts`).
- **In-process caches that load from the DB must be single-flight** (one loader behind a lock, like `ResumeCache`, #148): a cold-cache burst (a site build) otherwise exhausts the pool. Cache only what can't go stale (a saved run never changes) or key it by run.
- **Three snapshot readers, on purpose** (#152, #155): `snapshots_for_games` (every published snapshot, plus the rebuilt fallback: the game center's history chart), `current_snapshots` (only the one a page shows: boards, schedules, games of the week), `snapshots_for_season` (published only: the owner-only Book ledger and report; rebuilt forecasts must never reach it).
- **Read only what a page shows.** Full rows of both rating sets or every snapshot add up fast: the team page's history went 8 → 42 KB when the season gained ~90 runs until it read one compact row per run (#154); the home page read four full rankings for two Top 25s until `/rankings/top` (#155). Before adding a reader, profile it (`profile_api.py`) and save every affected response before/after for a byte-for-byte check (#154/#155 did this for all team pages and week boards).
- `tsi serve --reload` on Windows can stop reloading after the first change: restart it when results look stale.
- **The cache policy goes by path prefix** (`api/caching.py`): owner-only routes are `no-store` only because their prefix is listed. Moving them under `/cfb` (#183) would have made them publicly cacheable without new entries; a test now pins `/cfb/book` and `/cfb/model`. Add an entry (and a test) for any new private route.

## 5. The nightly job and CFBD

- `tsi run` takes ~35 s in Actions, mostly CFBD downloads. CFBD is slowest at the top of the hour (full-season advanced stats > 30 s at 11:00 UTC, ~15 s later; #144). The client has a 60 s read timeout, retries after 5 s / 30 s, honors `Retry-After` on 429, and runs same-endpoint requests one at a time.
- The ingest fetches its requests concurrently (`CfbdClient.prefetch`, #106): a new daily loader declares `requests(season)` and joins the prefetch in `services/results.py`.
- **Elo carry (#146):** live runs resume Elo from `model/artifacts/elo_carry.json` (end of last season) when the database's fingerprint of the 2014–2025 games and the Elo parameters match; otherwise the run logs "replaying all seasons" and reads every game (~3 MB more, numbers identical). Rebuild it (`tsi model carry`, on a local copy) after each season ends, with `tsi model fit`, and whenever Elo's k / HFA / carryover / division means change.
- **Component carry (#177):** last season's fitted components come from `model/artifacts/component_carry.json` when it was built for the season before, with the artifact's λ and version, and `offense_rows_fingerprint` (md5 of every column `offense_rows` returns, NULLs marked, floats as Postgres's shortest exact text) still matches; otherwise the run logs "saved component fit ... no longer matches" and fits it (~0.6 MB more, numbers identical). `tsi model carry` writes it with the Elo carry. **A refit that changes λ, the version or the fitting code needs a new carry** (fitting-code changes must bump the version). Built on Windows and used on Linux runners, values can differ in the last bit from a fresh fit (the Elo carry shows one rating 1 ulp apart between the two PCs); the publisher compares forecasts at 2 decimals, so that never republishes a game.
- The run reads this season's games and stats once and shares them between ratings, rankings and the sim (`LiveInputs.shares`, #147).
- **The FCS playoff bracket (#157):** CFBD lists the playoff games (notes "FCS Championship - …", filed as regular season) only after the NCAA announces the field on selection Sunday afternoon, after that morning's nightly run, and it has **no seeds or second-round pairings**. Enter each season's bracket by hand in `backend/src/tsi/sim/fcs_brackets.py` (24 slugs by position; check the quarterfinal pairings) and push before the next nightly run; the run checks the first round against CFBD's and ignores a mismatched bracket. Later rounds appear in CFBD only once the earlier round is played. Before #157 the FCS odds simply stopped when the playoff games appeared, which emptied `/playoff/fcs`.
- **Games of the week after Sunday (#157):** a later run in the poll week weighs only games whose `games.created_at` is after the picks (`created_at` is never overwritten by upserts, `NEVER_UPDATED`), and replaces a pick when the new game ranks better and the pick hasn't kicked off.
- **What a push changes, and when (lesson of 2026-11-23):** code that changes *stored* results (the sim, the games of the week, published forecasts) shows only after the next nightly run writes them; a site rebuild alone can't show them. Things the API computes per request from stored rows (rank arrows, #156) show as soon as Render serves the code and the page is rebuilt (a web push or the nightly refresh). Running the nightly job by hand costs ~3 MB plus the page refresh, and CFBD calls; the owner prefers waiting for 11:00 UTC.

## 6. Model and backtest workflow

- **Model changes:** rerun `tsi backtest run` (+ `tsi backtest book` for Book changes), then `tsi model fit`, and commit the new artifact. Save a backtest run after every model change: it is what `/model/report` serves (#76). A local save lands on the local/`dev` database; once the artifact is on `main`, the **Save backtest to production** workflow (`gh workflow run backtest.yml`, #110) saves it to production (it reads the history from production: **12.6 MB** on the local copy, a little more on production; fine a few times a season, never in a loop; #178). The artifact is written with LF, so an unchanged refit leaves git clean.
- **Backtest speed:** ~30 s each (`backtest book` reruns the margin backtest): ~825 daily refits × 6 ridge fits, a third in `np.linalg.solve` on ~530 columns. Vectorizing the rest saved nothing measurable (2026-11-05), and faster solvers would break bit-exact parity.
- **Parity:** dump every walk-forward pick (or rating, forecast, sim result) with `repr` floats before and after a change; refactors must be identical.
- **Season sim indexes:** FBS teams first, then FCS, then pooled opponents; FBS-only code (the CFP projector) relies on FBS being the first block. Adding teams or games changes every random draw: compare old vs. new within simulation noise.
- **Rebuilding missing days** (#152): `tsi rebuild verify` replays a stored nightly run and must match exactly; `tsi rebuild season` fills days without a run and games without a forecast (rating runs marked `params.job = "rebuild"`, `rebuilt_forecasts`, Sunday sims and games of the week); on production through the manual **Rebuild missing days** workflow (`rebuild.yml`), ~3 MB of Neon per day rebuilt. Re-running only fills what is still missing. A replay uses today's copy of past games, so CFBD's later corrections show (hundredths of a point).
- The experiment playbook is doc 09 §6.

## 7. Tests

- **DB tests** build the schema from the ORM, so the immutability trigger is loaded from the initial migration file (`tests/db_integration/conftest.py`). Shared builders live in `tests/factories.py`.
- **API tests** seed a tiny 2026 season (`tests/db_integration/api_seed.py`) and override `get_session` + `get_now` (clock pinned) on `create_app(...)`; the test client needs the `httpx2` dev dependency (Starlette 1.9).
- **gitleaks** flags realistic-looking fake keys in tests: use low-entropy values like `"fakekey"`.
- **Typer:** a command group with one command collapses into that command, so `CliRunner().invoke(group, ["cmd"])` fails with a usage error (exit 2) that can pass for an intended exit 2. Invoke through the root app (`tsi.cli.main.app`, `["neon", "transfer"]`) and assert on the output too (#179).
- **Playwright checks of the site:** scope locators (`page.locator("header").get_by_role("link", name="Rankings", exact=True)`): "Rankings" also matches "Full Rankings". Run scripts with `PYTHONIOENCODING=utf-8`, since the site's typographic minus (−) breaks printing on the cp1252 console.
- CI (`ci.yml`) runs on every push/PR and skips DB tests. Its web job runs `npm run check` only (types in sync, typecheck, lint, Prettier); it no longer builds the site (#191: each build read ~7 MB from Neon through the live API). Vercel's build is the site's build check: a failed deployment keeps the previous site live and emails the owner. Before a web push, run `npm run check` and the local screenshot checks (§9).

## 8. Deploying

- **Who deploys what:** the nightly job runs whatever is on `main` and writes to Neon `production` (`DATABASE_URL` secret, same as Render). The API runs what Render last deployed. The site is what Vercel last built.
- **Render deploys only commits that touch `backend/` and pass CI** (`rootDir: backend`, `checksPass`), and it looks at the **newest commit of a push** only: a backend commit followed by a web/docs commit in the same push is never deployed. Make the backend commit the last one in its push. If CI was red (or the fix touched only `web/`/docs), use Render's **Manual Deploy** and confirm the live API serves the change.
- **Vercel builds only pushes that change `web/`** (`web/vercel.json` `ignoreCommand`, #144). Vercel skips the build on exit 0, builds on exit 1, and **fails the deployment on any other exit code**: on 2026-11-20 the last successful deployment (`ded3e03`) wasn't in Vercel's shallow clone, `git diff` exited 128 and the build failed. The command now checks the commit exists first and turns every error into 1 (build).
- **Ship API changes before the site** (#90): Vercel prerenders pages from the *live* API, and its build finishes before Render deploys. Push the backend, wait until the live API serves the change, then push the web (or redeploy the site).
- **Breaking API changes span two deploys:** add the new fields first and keep the old ones until the live site no longer reads them (`Playoff.format` → `rounds`, #125).
- **The spec and the generated types travel together.** CI's web job fails when `web/lib/api/schema.d.ts` doesn't match `docs/api/openapi.json` ("Generated types are not up-to-date"), and then Render deploys nothing. When a backend change updates the spec but the site code that uses it must wait (ship the API first, #90), put the regenerated `schema.d.ts` / `types.ts` (harmless on their own) in the same push as the backend, with a backend commit last; push the site code once the live API serves the change (2026-11-20: e2fedab failed CI this way).
- **API changes:** run `tsi openapi` and commit `docs/api/openapi.json` (else `tests/api/test_openapi.py` fails), then `npm run api:types` in `web/` and commit `lib/api/schema.d.ts` (else `npm run check` fails). Response shapes are the dataclasses in `services/read/`; the web imports them via `lib/api/types.ts`.
- **An additive API field the site shows** (#188, #190): push the backend with the regenerated spec and types (the site code untouched), wait until the live API serves the field, then push the site. Waiting matters: pages are rebuilt from the live API and then refreshed only nightly, so a site pushed first shows the page without the field until the next morning. Wait with a bounded background loop (`for i in $(seq 1 30); do curl ... | grep -q '"field"' && exit 0; sleep 30; done; exit 1` with `run_in_background`), not foreground sleeps; commit the site locally meanwhile.
- **Moving addresses** (#183–#185): mount new API paths beside the old ones (`legacy_` operation ids keep the spec's ids unique), switch the site and the nightly job, confirm the live site serves the new pages (an old address answering 308), then drop the old paths.
- **Migration order:** a migration that **adds** what new code needs runs **before** pushing that code; one that **drops** a column runs **after** the code that stops mapping it is live (the ORM selects every mapped column). A rename is add → code switch → drop.
- **Migrating before the code is on `main`:** the **Migrate production** workflow checks out a ref. Push a temporary branch from `origin/main` (a `git worktree` keeps the main checkout untouched) holding only the migration file (no `web/` change, so Vercel skips it), `gh workflow run migrate.yml --ref <branch>`, confirm `Running upgrade` in its log, delete the branch, then push `main` with the backend commit last (done for #145).
- **GitHub Actions:** `astral-sh/setup-uv` has no floating major tag; pin the exact version (e.g. `v10.3.0`).

## 9. Web

**Next.js 16**
- Newer than training data: read the guide in `web/node_modules/next/dist/docs/` before writing Next.js code (`web/AGENTS.md`; `next dev` rewrites that file, commit it as is). Cache Components are on (`"use cache"` + cache tags, not `revalidate` exports).
- Visited pages stay in the document, hidden (React Activity, up to 3 routes): a page's `<style>` or other global side effect keeps applying after you leave. Set globals in a `useLayoutEffect` and undo them in its cleanup (`components/team/page-team-light.tsx`).
- **"A `use cache` function is awaiting a promise created outside it"** in `next dev` is a false alarm when the API is slow (a Render cold start): the dev server reruns the call after 10 s and blames shared state. Dev-only; builds allow 162 s. Warm the API first (`curl …/meta/current`).
- `next start` locally answered 500 on team, week and rankings pages after `/api/revalidate` ("`usePathname()` … outside of `<Suspense>`", 2026-11-09) while the live site was fine. Unexplained; don't rely on `next start` for checks.

- **Server and client components:** a server component (the header) gets a client reference, not the value, when it imports data from a `"use client"` module, and functions can't be passed to client components: `SPORTS.map is not a function` broke every page with a 500 (#183). Keep shared data plain (strings, not `match` functions) in `lib/`.
- **One header dropdown at a time** (#194): the search and the sport menus share `components/layout/header-layer.ts` (an external store); while search is open the sport menus are invisible under its box. Close header dropdowns on a click, not a press, when closing changes the layout: the shift moved the target before the click landed.
- **Hover menus** (`components/layout/sport-menu.tsx`, #186): keep which menu is open in one shared state, so opening one closes the others at once; per-menu close delays left the previous menu showing. Derive "closed after a page change" from the page it was opened on (React's lint rejects `setState` inside an effect). A mouse click after hovering must only open (event timing could toggle it shut).
- **Every page address comes from `lib/routes.ts`** (`cfb.team(slug)`, `cfb.schedule(season, week, division)`, ...; #184): college football lives under `/cfb`; the old addresses redirect (308) in `next.config.ts`.

**Data and caching**
- **Only through `web/lib/api/queries.ts`** (server-only, `"use cache"` + `cacheLife("tsi")` + tags); never `fetch` the API elsewhere. Data the browser needs (the header search's team list, #193) goes through a route handler that calls those cached functions (`app/cfb/search-index/route.ts`: prerendered, refreshed by the nightly revalidation); with the same arguments as a page it shares that page's cache entry, so it adds no API or Neon reads. The browser fetches such a file once and works locally; never per keystroke. New `cacheLife` profiles need `next typegen` (part of `npm run typecheck`).
- **The `tsi` profile re-checks daily** (#145); the nightly `/api/revalidate` (`revalidateTag("tsi", { expire: 0 })`, roadmap 12.2) updates pages. Anything that must change during the day happens in the browser: a game's state (scheduled / in progress / final score pending / final) comes from the viewer's clock (`lib/game-phase.ts`, `components/game/game-phase.tsx`: `useGamePhase` in client components, `PhaseScope` + `When` / `PhaseLabel` around server-rendered parts; #149).
- **Team page sections appear for every ranked team** (owner, #90): when an input is missing, show the section with that value left out, never hide it.

**Look (#167, #168, #171; doc 06 "Accents")**

A component class that must override a utility on the same element (`.tsi-lit-hover:hover` vs. the card's `border-border` / `bg-card`) goes in `@layer utilities` (#169: the home cards showed no hover for that reason once the glow was gone).

The site picks the shown color per theme in `web/lib/format/color.ts` (never white/black/gray; lifts a too-dark color in its own hue). **iPhones and browser chrome (#165, #166, #174, #176)**
- `viewport-fit=cover`; the header pads by `safe-area-inset-top`, the bottom bar by the bottom inset, sides by `.tsi-safe-x`. Playwright can't emulate a notch: check on a real iPhone.
- **In a normal Safari tab iOS paints the strip behind the clock with the `<body>` background**, not the root's and (in newer Safari) not `theme-color`. So `html`, `body` and the header share the panel color, and the page color sits on a full-width wrapper below the header (`app/layout.tsx`). ## 10. Windows shell and tools

- PowerShell here-strings mangle inline Python: write scripts to the scratchpad and run them with `python -I` from a neutral directory (a local `types.py` once shadowed the stdlib). `python -I` drops the script's own folder from `sys.path`: use `PYTHONPATH` for helper modules next to a script.
- Shell heredocs turn `\n` inside Python strings into real newlines: write edit scripts with the Write tool, or use the Edit tool.
- **Line endings:** Python on Windows writes CRLF in text mode. Git normalizes most files to LF on commit (`.gitattributes` `* text=auto eol=lf`), but files under `.claude/` have `text` unset and are committed as written: edit them with `open(p, encoding="utf-8", newline="")` (or the Edit tool) so they stay LF (a runbook edit on 2026-11-23 went in as CRLF and needed a follow-up commit).
- **An anchor that appears twice** (two identical lines) fails a count-once assertion: replace both on purpose (`sed .../g`, then grep the result). Quotes in heredoc Python (`\'`) can stop an anchor from matching: for edits with quotes, prefer the Edit tool or a script written with the Write tool.
- **Edit scripts must assert their anchors** and the commit's file list must be checked: on 2026-11-23 a Python syntax error stopped a docs edit, the shell carried on, and the code commit went out without its doc change (fixed in a docs-only follow-up).
- Commit messages: bash heredoc + `git commit -F` (PowerShell `Set-Content` adds a BOM). `sed` replacements containing `#` need another delimiter.
- The console is cp1252: set `PYTHONIOENCODING=utf-8` (or write to a file) to print ★/–; use `%#I`, not `%-I`, in `strftime`.
- Git Bash rewrites arguments that start with `/` into Windows paths: prefix such commands with `MSYS_NO_PATHCONV=1`.
- **Stopping a background `npx next dev` leaves its Node server running** (three times on 2026-11-23): the next start fails with `EADDRINUSE`, or a stale server answers with old code (a 500 that looked like a new bug). After stopping it, check the port (`Get-NetTCPConnection -LocalPort 3005 -State Listen`), confirm the owning PID's command line is this repo's `next/dist/server/lib/start-server.js`, and stop that one PID.
- **`next dev` can miss an edit to `app/globals.css`** (2026-11-24: a new base rule never reached the page until the dev server restarted). When a CSS change seems to do nothing, check the served stylesheet (`/_next/static/chunks/…css`) before debugging, and restart the dev server.
- **Stale `next dev` processes** survive sessions and can keep a port or lock `web/.next/dev`: list `node` processes with their command lines (`Get-CimInstance Win32_Process`, or `Get-NetTCPConnection -LocalPort 3005 -State Listen`) and stop the stale one before starting another or deleting `.next`. Deleting `.next` under a running dev server crashes it; a stale one can serve old CSS.
- The auto-mode permission check blocks disabling a workflow (`gh workflow disable`: ask the owner to run it) and stopping processes matched broadly by name (stop the one PID you started, after checking its command line).
- The artifact tools reject the short `GAGESW~1` temp path as `out_dir`; use the full `C:\Users\Gage Swann\...` path.
